# ADR-0000：使用 ADR 記錄架構決策

| 狀態 | 已接受 |
|------|--------|
| 日期 | 2024-01-01 |
| 作者 | @leonwong282 |
| 決策者 | 專案維護者 |

## 背景

隨著本專案的成長，我們需要一種方式來記錄重要的架構決策，以便：

- 新貢獻者了解為什麼以某種方式建構
- 我們不會重複討論相同的決策
- 我們有專案演變的歷史記錄
- 決策可以隨時間審查和更新

## 決策驅動因素

- 需要決策過程的透明度
- 希望減少新貢獻者的上手時間
- 想要避免「我們為什麼這樣做？」的討論
- 需要輕量級、對開發者友善的文件格式

## 考慮的選項

1. **架構決策記錄（ADR）** - 儲存庫中的 Markdown 檔案
2. **Wiki 頁面** - GitHub Wiki 或外部 wiki
3. **Issue 評論** - 在 GitHub issues 中記錄決策
4. **Confluence/Notion** - 外部文件平台

## 決策結果

選擇的選項：**「架構決策記錄（ADR）」**，因為它們：

- 與程式碼一起進行版本控制
- 可通過正常的 PR 流程進行審查
- 輕量且易於建立
- 可搜尋且易於發現
- 不依賴外部服務

### 正面影響

- 決策以一致的格式記錄
- 歷史記錄保存在 git 中
- 易於在程式碼註解和 PR 中引用
- 不需要額外的工具

### 負面影響

- 需要紀律為重要決策建立 ADR
- 需要維護的另一件事（緩解措施：保持流程輕量）

## 各選項的優缺點

### 儲存庫中的 ADR

- ✅ 與程式碼一起進行版本控制
- ✅ 經過 PR 審查
- ✅ 無外部依賴
- ✅ 如果更換平台可以移植
- ❌ 需要貢獻者的紀律

### Wiki 頁面

- ✅ 易於編輯
- ❌ 與程式碼儲存庫分離
- ❌ 沒有 PR 審查流程
- ❌ 經常變得過時

### Issue 評論

- ✅ 已經在 GitHub 中
- ❌ 之後難以找到
- ❌ 在對話中容易遺失
- ❌ 沒有結構化的格式

### 外部平台

- ✅ 豐富的編輯功能
- ❌ 需要維護另一個工具
- ❌ 存取控制複雜
- ❌ 供應商鎖定
